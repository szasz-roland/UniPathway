# CLAUDE.md

Context for Claude Code (or any AI assistant) working in this repo.

## What this is

Órarend is a personal university schedule web app: a static site with zero build step, split into [index.html](index.html) (markup), [css/style.css](css/style.css), and [js/script.js](js/script.js) — plain `<link>`/`<script src>`, no bundler, no module system (see the file-layout note under "Code conventions" for why not ES modules specifically). It's being converted into an installable, offline-capable PWA hosted on Vercel — see [ROADMAP.md](ROADMAP.md) for the phased plan and current priorities.

Beyond the core weekly schedule, it now also has: light/dark theme switching; a checklist/todo feature (shopping lists with price tracking, task lists), persisted in `localStorage`; JPG/PDF schedule export; a second person's timetable (`ZOLI_EV`) alongside your own as its own nav entry; a from-scratch "Teremkereső" room search (scoped to just your own classes' rooms) with an embedded-map toggle; and a course action sheet (tap a class or an online-course chip → "Terem keresése" jumps to its room pre-filtered, "Tantárgy infó" shows a structured info/requirements summary sourced from real Neptun course pages). See "Code conventions" below for how each of these actually works before touching them.

## History (for context, not action items)

The app started as a single HTML file wrapped into a native Android APK via [Web2APK](https://github.com/77AXEL/Web2APK). That involved fixing `INSTALL_FAILED_INVALID_APK` (zipalign / resources.arsc compression), `INSTALL_PARSE_FAILED_NO_CERTIFICATES` (switching from `jarsigner` v1 to `apksigner` v2/v3), a status-bar rendering bug (edge-to-edge drawing over a transparent status bar — fixed via `styles.xml` + `fitsSystemWindows`), a missing `android.permission.INTERNET` entry in the wrapper's manifest (the WebView could load its own bundled assets but silently couldn't reach any CDN), and — once the app started reading its own bundled local assets via JS (`course_data/*.json`) — a WebView that by default can't `fetch()`/XHR its own `file:///android_asset/` files at all (fixed by adding `setAllowFileAccessFromFileURLs(true)`/`setAllowUniversalAccessFromFileURLs(true)` to `MainActivity`, plus switching the app's own JS off `fetch()` — see the "Local JSON reads" note under Tantárgy infó below, that half of the fix lives in this repo). The `android/` directory is a leftover from that phase; it's not part of the active build and can be deleted once the PWA fully replaces it.

Rebuilding/reinstalling an APK on every schedule change was the reason for pivoting to a PWA — and the JPG/PDF export feature has surfaced another reason: it works in every real browser but still fails silently in the Web2APK wrapper even after the INTERNET permission fix, most likely because that wrapper's bare-bones `MainActivity` never registers a `DownloadListener` and modern WebView blocks top-level navigation to `data:` URLs. See [DEPLOYMENT.md](DEPLOYMENT.md#2-export-jpgpdf-doesnt-work-in-the-android-apk-wrapper) for the full writeup. Don't try to fix this from `index.html` — it's a native-wrapper gap, not an app bug, and the fix is finishing the PWA/hosting work below, not patching the wrapper further.

## Code conventions

- No frameworks, no build tooling for the app's own code. Keep it vanilla HTML/CSS/JS unless a roadmap phase explicitly calls for a dependency (e.g. a data backend in Phase 2). The two exceptions that do exist are documented below (export libraries) — don't add further runtime dependencies without calling it out the same way.
- File layout: `index.html` (markup + the two CDN `<script>` tags + a tiny inline theme-init `<script>` in `<head>`), `css/style.css` (everything that was the old inline `<style>` block), `js/script.js` (everything that was the old inline `<script>` block — all the data arrays, all the render functions). `assets/` holds `icon.png` (used both as the web favicon and as `wa.py -icon`'s input when rebuilding the Android APK — if you ever move it again, update both the `<link rel="icon">` href *and* tell whoever runs the APK build script to update their `-icon` path). `data/` holds `myCourses.xlsx`/`zoliCourses.xlsx`, the raw Neptun exports kept as reference — nothing in the app reads them at runtime, they're source material for hand-maintaining `EV`/`ZOLI_EV`. `course_data/` (JSON, fetched at runtime by `fetchLocal()`) intentionally stays at the root rather than nesting under `data/` — see the Tantárgy infó section below for why.
  - **The head's inline theme-init script stays inline, deliberately** — it sets `data-theme` before first paint to avoid a flash of the wrong theme, which only works if it runs synchronously with zero network/file round-trip. Moving it into `js/script.js` would reintroduce the flash. Same reasoning for keeping the two CDN `<script>` tags as direct `<script src>` in the HTML rather than importing them from `js/script.js`.
  - **`js/script.js` is a classic script (`<script src="js/script.js">`), not an ES module — don't add `type="module"` or `import`/`export`.** This app is opened both as a normal page and as `file:///android_asset/index.html` inside the Web2APK wrapper (see History), and ES module loading is subject to the same CORS/fetch-style restrictions that already broke `fetch()` for local files there (see the `fetchLocal()` note below) — `type="module"` would silently fail to load the whole app over `file://`. A plain `<script src>` (like a plain `<link rel="stylesheet">`) uses the ordinary resource-loading pipeline instead, which has no such restriction and is confirmed working over `file://`.
- CSS custom properties in `:root` drive theming — `--rail` (dark sidebar, theme-invariant — it's always dark), `--bg`/`--ink`/`--ink-2`/`--faint`/`--hair`/`--surface-2` (light-mode main area, redefined under `[data-theme="dark"]`), and per-subject color pairs (`--ea-*`, `--gy-*`, `--pr-*`, `--mt-*`, also redefined per theme). Reuse these rather than hardcoding colors — the rail/drawer/nav UI is theme-invariant by design and never needs dark-mode overrides.
- Theme: `applyTheme('light'|'dark')` sets `data-theme` on `<html>` and persists to `localStorage['orarend-theme']`; an inline script in `<head>` (before the stylesheet) applies the saved/system preference immediately to avoid a flash of the wrong theme. Toggled from the settings panel (gear icon).
- Checklists: persisted as one JSON blob in `localStorage['orarend-checklists-v1']` (see `loadChecklists`/`saveChecklists` and the `createChecklist`/`addItem`/etc. helpers). This is genuinely private to one browser — no sync across devices, since there's no backend. New checklists get a preset icon per category (`CATS`) and a color cycled from `COLOR_CYCLE` (the same 4 subject accent pairs used elsewhere) — don't add a custom icon/color picker unless asked, that was a deliberate scope decision.
- Schedule data lives in arrays at the top of the script: `EV` (your own timed classes), `ONLINE` (async/no-fixed-time courses), `CODES` (registration codes). Phase 2 moves this out of the source file.
- Other people's schedules (e.g. `ZOLI_EV` for a friend's timetable) follow the same `EV` shape (`[dayIndex, start, end, name, room, who, type, pref?]`) and get their own `NAV_LINKS` entry. `ZOLI_EV` is transcribed from that friend's own Neptun export (`data/zoliCourses.xlsx`, same format as `data/myCourses.xlsx`) — prefer re-parsing an updated export over hand-editing individual entries if he changes course, so room/instructor text stays byte-for-byte what Neptun says (a past hand-transcription from a screenshot got both a room name wrong and invented a consultation session that turned out not to exist — the xlsx export is the trustworthy source, a screenshot isn't). `isScheduleView(view)`/`datasetFor(view)` (near the top of the script) are what let `rail()`, `day()`, `week()`/`buildWeekGrid()`, and `renderHead()` work generically across any schedule-shaped view instead of hardcoding `EV` — add a new person by adding their array + a `datasetFor` branch + a nav entry, not by duplicating rendering logic. Room/instructor are optional (`who` may be `""`; the footer template skips the separator when it's empty) since a borrowed schedule often doesn't have that detail. Export (JPG/PDF) always exports your own `EV`, not another dataset — that's deliberate, not an oversight.
- Room search (`ROOMS` array, "Teremkereső" nav entry, `renderRoomSearch()`/`renderRoomResults()`): a from-scratch reimplementation of `u-szeged.hu/teremkereso`'s search (room code/name/building lookup), not a live integration with it — that site has no CORS headers and no HTTPS, so it can't be called from a browser at all once this app is hosted, and its data was only reachable by POSTing search terms to its PHP endpoint and scraping the HTML response (no JSON API). `ROOMS` is deliberately scoped to **only the rooms used in your own `EV` timetable** (currently 8 entries covering 7 distinct classes), not the full ~700-room university database (IDs run roughly 1–771) — that scoping was an explicit user decision, not a shortcut; if it ever needs to grow (e.g. to cover `ZOLI_EV` too), re-scrape the same way (see git history for the search.php POST pattern) rather than bulk-importing everything.
  - Some of `EV`'s room labels don't literally match teremkereső's canonical room name, so matching is done through an optional `aliases` array per room (checked in `matchesRoom()` alongside code/name/dept/address): `IR-213-3`'s canonical name is "Irinyi 213 tanterem" but `EV` calls it "Irinyi 213 PC-terem"; `TIK-002-0` ("TIK Nagyelőadó") is aliased to "TIK Kongresszusi terem" (confirmed with the user — teremkereső has no room literally called that, this was the only large-hall candidate in that building); and `EV`'s "TIK Alagsor I-II. Előadó" is aliased onto *both* `TIK-A01-0` and `TIK-A02-0` since which specific one is used couldn't be determined and the user chose to show both rather than guess. If you add a room whose `EV` label doesn't match its teremkereső name verbatim, give it an `aliases` entry rather than editing `name` — `name` should stay what teremkereső actually calls it.
  - The map toggle uses `https://www.google.com/maps?q=<address>&output=embed` (a no-API-key embed URL keyed off the room's address string) instead of the original site's approach (a hardcoded 67-entry address→iframe lookup table in its `get-map.js`) — ours generates the embed from whatever address is in the data, so it isn't limited to a fixed address list.
- Course action sheet: tapping a day-view course card (`.item .card` in `day()`, the ones with the little arrow) or an online-course chip (`.drchip` in `renderCodepage()`'s `online` branch) opens a bottom sheet (`#courseSheet`/`#sheetScrim`, `openCourseSheet()`/`closeCourseSheet()`) listing things you can do with that course. `openCourseSheet(course)` takes either a scheduled-course object (`{name,s,en,room,who,type}`, from `EV`/`ZOLI_EV`) or an online one (`{name,meta,online:true}`, from `ONLINE`) — the `online` flag is what suppresses the "Terem keresése" button (no fixed room to search for) while keeping "Tantárgy infó". This is meant to grow (more `.sheet-action` rows) as more per-course actions get added — don't build a second, separate popup mechanism for the next one. Only wired up on the day-list view, not the desktop week grid (`buildWeekGrid()`'s `.wcard` has no arrow/click handler) — that was a deliberate scope match to "the courses that already look clickable," not an oversight. Not wired up on the `CODES` page rows (Kötelező tárgyak/Kritérium) either — those already have their own click-to-copy interaction and the same courses are reachable via `EV`/`ONLINE` anyway.
- Tantárgy infó ("Tantárgy infó" sheet action, `COURSE_DOC_ALIASES`, `showCourseInfo()`, `docSection()`): a structured per-course info bank at `course_data/<slug>.json`, built from real course pages saved as PDFs from `unics.szte.hu` (that site needs a login too, so this only works because the user is logged in there themselves and exports the page — same non-scraping constraint as Teremkereső, see above). Each JSON has `name`/`code`/`instructor`/`summary`/`topics[]`/`grading[]`/`rules[]`/`links[]`/`updated` — condensed and reorganized from the source PDF's prose into short bullet points (deliberately *not* a raw text dump, per an explicit user request for "an optimal information bank" rather than "a big chunk of text"), but preserving exact numbers (grading thresholds, deadlines) since those are the parts that actually matter and are easy to get subtly wrong when condensing.
  - **Local JSON reads use `fetchLocal()` (an `XMLHttpRequest` wrapper), never `fetch()`.** `fetch()` unconditionally refuses `file://` URLs in every Chromium engine — confirmed directly (`TypeError: Failed to fetch` / "URL scheme 'file' is not supported"), this is a hard scheme restriction with no settings-based override, not something the Web2APK wrapper's WebView config can fix. Since this app is opened both as a normal page and as `file:///android_asset/index.html` inside that wrapper, any future local-asset read must go through `fetchLocal()`/XHR too, or it'll silently work in a browser and silently fail (empty catch → "nincs feltöltve"-style fallback) in the wrapped app — this exact bug already happened once for `course_data`. XHR to `file://` still depends on the wrapper's `WebSettings.setAllowFileAccessFromFileURLs(true)`/`setAllowUniversalAccessFromFileURLs(true)` (added to `MainActivity.smali` in the external Web2APK project alongside the earlier `INTERNET` permission fix — see History above and DEPLOYMENT.md) — that part could only be reasoned through from documented Android WebView behavior and couldn't be verified locally, since desktop Chromium has no equivalent override and blocks file XHR unconditionally too (confirmed separately) regardless of any setting.
  - The sheet is color-coded per course: `openCourseSheet()` calls `applySheetAccent(course.type)`, which sets `--sheet-bg`/`--sheet-tx`/`--sheet-ac` on `#courseSheet` to that course's existing `--{type}-bg/-tx/-ac` tokens (`type` is `EV`/`ZOLI_EV`'s existing `ea`/`gy`/`pr`/`mt` field; `ONLINE` courses don't have one, so `renderCodepage()` assigns one via `COLOR_CYCLE[i%4]` when building the chip). This is deliberately the *same* four-color system every class card already uses, not a new palette — the info sheet for a course should look like it belongs to that course's card. `GRADE_COLOR_RULES`/`gradeColor()` additionally color-code grading list items by outcome (red→green across elégtelen/elégséges/közepes/jó/jeles) regardless of course accent, since grade-quality color coding is a stronger, more universally legible signal than the subject color for that specific data. Watch for the `\bjó\b` trap if editing these rules: JS's `\w`/`\b` are ASCII-only, so a boundary immediately after an accented vowel like "ó" doesn't match — that's why the "jó" rule uses a lookahead (`(?=\s|\(|$)`) instead of a trailing `\b`.
  - `COURSE_DOC_ALIASES` maps every `EV`/`ONLINE` display-name string to its `course_data` slug, because those names frequently don't match the source page's title verbatim (`EV`'s "Matematika 1. ea." → `matematika-informatikusoknak-1-ea.json`; `ONLINE`'s "MI az egyetemi tanulmányokban" → `mesterseges-intelligencia-az-egyetemi-tanulmanyokban.json`; both `ONLINE` "Webfejlesztés alapjai (ea)" *and* "Webfejlesztés alapjai gy." point at the same `webfejlesztes-alapjai-coursera.json` since Neptun treats the Coursera-based ea/gy as one combined completion). When adding a new course's info, add a `course_data/<slug>.json` file *and* an alias entry for every name string that course appears under — a name that resolves to no alias just shows a friendly "nincs infó" fallback (`showCourseInfo()`'s catch path), it doesn't error.
  - The raw PDF sources live in `course_info_req/` (gitignored — large, and personal-ish exports, not meant for the public repo). The two earlier folders `course_info/`/`course_req/` (plain-text, one file per course, split by info vs. requirements) were an earlier iteration of this same feature and are now unused/gitignored — `course_data/` (structured JSON, info + requirements combined into one file per course) superseded them once the source shifted from hand-typed txt files to real exported PDFs. Don't resurrect the old two-folder txt approach.
- Export (JPG/PDF, in the settings panel) uses `html2canvas` + `jsPDF`, loaded via pinned CDN `<script defer>` tags — the one deliberate exception to "no dependencies" here, since there's no native browser way to rasterize a DOM subtree to an image. `buildWeekGrid()` is reused for both the on-screen desktop week view and the export capture (rendered off-screen via `.export-capture`, which force-overrides the CSS variables to light-mode values and disables the `.wcol` entrance animation, regardless of the active theme). `runExport()`/`exportSchedule()` surface load/render failures as a visible error message (`.export-err`) instead of failing silently — verified working in real browsers; **known not to work in the Web2APK Android wrapper** even with network access fixed, see [DEPLOYMENT.md](DEPLOYMENT.md) — that's a wrapper limitation (no `DownloadListener`), not something to chase in this file.
- Font: "Plus Jakarta Sans" via Google Fonts.
- UI language is Hungarian; keep new user-facing strings in Hungarian unless told otherwise.

## Security / repo hygiene

- This repo is meant to eventually be public on GitHub, so treat it as if it already were — but as of now (2026-09-07) it has **no GitHub remote configured at all**; every commit so far is local-only (see [DEPLOYMENT.md](DEPLOYMENT.md) for status). Never commit signing keys, `.env` files, API tokens, or Vercel/Firebase/Supabase credentials — see [.gitignore](.gitignore). If Phase 2/3 introduces a backend or push notifications, secrets belong in Vercel environment variables, not in the repo.
- The schedule data (professor names, room numbers, course codes) is ordinary public university catalog information, not sensitive — no need to redact it.
- The `android/` build output contains no signing material currently, but double-check before adding gradle/keystore files later.
- Checklist data (shopping items, task names, prices) lives only in the visitor's own browser `localStorage` — never sent anywhere, not a server-side concern. It's still real user data now, though (the app's first), so don't casually wipe/reset the storage key from code.
- `html2canvas`/`jsPDF` are loaded from cdnjs over HTTPS with pinned exact versions (see index.html's `<script>` tags) — if bumping versions, keep them pinned, don't switch to a `@latest`-style URL.
- **Access control lives entirely outside this repo.** The live site (`orarend.szaszroland.hu`) is gated by Cloudflare Access at the DNS edge (email allow-list + one-time PIN / Google login) — see [README.md](README.md#deployment--access). Do not add in-app passwords, login forms, or auth middleware to "secure" the app; that would duplicate/weaken a control that's already handled correctly upstream. If that architecture ever changes, update this note and the README section together.

## Working style notes

- This is a personal, low-stakes project — prefer small, direct changes over heavy abstraction. It's already split into `index.html`/`css/style.css`/`js/script.js` (the first Phase 1 restructuring step, see ROADMAP.md) — don't re-inline CSS/JS back into `index.html`, and don't split `js/script.js` further into multiple files/modules without a real reason (see the ES-modules note under Code conventions for why not modules specifically).
- **Commit workflow: implement, let the user try it, ask if it's good, then commit.** After finishing a feature/fix, don't commit immediately — wait for the user to confirm it works as expected first, then commit. Exception: pure documentation-only updates (like this file, ROADMAP.md, DEPLOYMENT.md) can be committed right away since there's nothing to "try."
- **Animation and design work goes through `.claude/skills/`.** Before writing any CSS motion or UI polish in this repo, use the relevant skill instead of freehanding it — for this vanilla CSS/JS app that's mainly `find-animation-opportunities` (sweep for what's worth animating and what isn't), `animate` + its `RECIPES.md` (the actual implementation: tool choice, easing tokens `--ease-out`/`--ease-in-out`/`--ease-drawer`, durations), and `animation-vocabulary`/`review-animations` for terminology and self-review. (`animate-expo`, `write-swift`, `pick-ui-library` target other stacks — not relevant here.) This folder is gitignored (third-party skill packages, unclear license) — it's a local tool, not part of the published repo.
