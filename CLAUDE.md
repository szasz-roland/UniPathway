# CLAUDE.md

Context for Claude Code (or any AI assistant) working in this repo.

## What this is

Órarend is a personal university schedule web app: a static site with zero build step, split into [index.html](index.html) (markup), [css/style.css](css/style.css), and [js/script.js](js/script.js) — plain `<link>`/`<script src>`, no bundler, no module system (see the file-layout note under "Code conventions" for why not ES modules specifically). It's being converted into an installable, offline-capable PWA hosted on Vercel — see [ROADMAP.md](docs/ROADMAP.md) for the phased plan and current priorities.

Beyond the core weekly schedule, it now also has: light/dark theme switching; a checklist/todo feature (shopping lists with price tracking, task lists), persisted in `localStorage`; JPG/PDF schedule export; a second person's timetable (`ZOLI_EV`) alongside your own as its own nav entry; a from-scratch "Teremkereső" room search (scoped to just your own classes' rooms) with an embedded-map toggle; and a course action sheet (tap a class or an online-course chip → "Terem keresése" jumps to its room pre-filtered, "Tantárgy infó" shows a structured info/requirements summary sourced from real Neptun course pages). See "Code conventions" below for how each of these actually works before touching them.

## History (for context, not action items)

The app started as a single HTML file wrapped into a native Android APK via [Web2APK](https://github.com/77AXEL/Web2APK). That involved fixing `INSTALL_FAILED_INVALID_APK` (zipalign / resources.arsc compression), `INSTALL_PARSE_FAILED_NO_CERTIFICATES` (switching from `jarsigner` v1 to `apksigner` v2/v3), a status-bar rendering bug (edge-to-edge drawing over a transparent status bar — fixed via `styles.xml` + `fitsSystemWindows`), a missing `android.permission.INTERNET` entry in the wrapper's manifest (the WebView could load its own bundled assets but silently couldn't reach any CDN), and — once the app started reading its own bundled local assets via JS (`course_data/*.json`) — a WebView that by default can't `fetch()`/XHR its own `file:///android_asset/` files at all (fixed by adding `setAllowFileAccessFromFileURLs(true)`/`setAllowUniversalAccessFromFileURLs(true)` to `MainActivity`, plus switching the app's own JS off `fetch()` — see the "Local JSON reads" note under Tantárgy infó below, that half of the fix lives in this repo). The `android/` directory is a leftover from that phase; it's not part of the active build and can be deleted once the PWA fully replaces it.

Rebuilding/reinstalling an APK on every schedule change was the reason for pivoting to a PWA — and the JPG/PDF export feature has surfaced another reason: it works in every real browser but still fails silently in the Web2APK wrapper even after the INTERNET permission fix, most likely because that wrapper's bare-bones `MainActivity` never registers a `DownloadListener` and modern WebView blocks top-level navigation to `data:` URLs. See [DEPLOYMENT.md](docs/DEPLOYMENT.md#export-jpgpdf-doesnt-work-in-the-android-apk-wrapper) for the full writeup. Don't try to fix this from `index.html` — it's a native-wrapper gap, not an app bug, and the fix is finishing the PWA/hosting work below, not patching the wrapper further.

## Code conventions

- No frameworks, no build tooling for the app's own code. Keep it vanilla HTML/CSS/JS unless a roadmap phase explicitly calls for a dependency (e.g. a data backend in Phase 2). The two exceptions that do exist are documented below (export libraries) — don't add further runtime dependencies without calling it out the same way.
- File layout: `index.html` (markup + the two CDN `<script>` tags + a tiny inline theme-init `<script>` in `<head>`), `css/style.css` (everything that was the old inline `<style>` block), `js/script.js` (everything that was the old inline `<script>` block — all the render functions, no longer the data itself, see below). `docs/` holds the working/planning docs (`ROADMAP.md`, `DEPLOYMENT.md`, `TODO.md`) — excluded from the Vercel deploy via `.vercelignore` since they're internal notes, not part of the app — `README.md`, `LICENSE`, `SECURITY.md`, and this file stay at root since GitHub and Claude Code both expect them there. `assets/` holds `icon.png` (used both as the web favicon and as `wa.py -icon`'s input when rebuilding the Android APK — if you ever move it again, update both the `<link rel="icon">` href *and* tell whoever runs the APK build script to update their `-icon` path). `data/` holds `myCourses.xlsx`/`zoliCourses.xlsx`, the raw Neptun exports kept as reference — nothing in the app reads them at runtime, they're source material for hand-maintaining `schedule_data/ev.json`/`schedule_data/zoli.json`. `course_data/` and `schedule_data/` (both JSON, both fetched at runtime by `fetchLocal()`) intentionally stay at the root rather than nesting under `data/` — see the Tantárgy infó section below for why.
  - **The head's inline theme-init script stays inline, deliberately** — it sets `data-theme` before first paint to avoid a flash of the wrong theme, which only works if it runs synchronously with zero network/file round-trip. Moving it into `js/script.js` would reintroduce the flash. Same reasoning for keeping the two CDN `<script>` tags as direct `<script src>` in the HTML rather than importing them from `js/script.js`.
  - **`js/script.js` is a classic script (`<script src="js/script.js">`), not an ES module — don't add `type="module"` or `import`/`export`.** This app is opened both as a normal page and as `file:///android_asset/index.html` inside the Web2APK wrapper (see History), and ES module loading is subject to the same CORS/fetch-style restrictions that already broke `fetch()` for local files there (see the `fetchLocal()` note below) — `type="module"` would silently fail to load the whole app over `file://`. A plain `<script src>` (like a plain `<link rel="stylesheet">`) uses the ordinary resource-loading pipeline instead, which has no such restriction and is confirmed working over `file://`.
- CSS custom properties in `:root` drive theming — `--rail` (dark sidebar, theme-invariant — it's always dark), `--bg`/`--ink`/`--ink-2`/`--faint`/`--hair`/`--surface-2` (light-mode main area, redefined under `[data-theme="dark"]`), and per-subject color pairs (`--ea-*`, `--gy-*`, `--pr-*`, `--mt-*`, also redefined per theme). Reuse these rather than hardcoding colors — the rail/drawer/nav UI is theme-invariant by design and never needs dark-mode overrides.
- Theme: `applyTheme('light'|'dark')` sets `data-theme` on `<html>` and persists to `localStorage['orarend-theme']`; an inline script in `<head>` (before the stylesheet) applies the saved/system preference immediately to avoid a flash of the wrong theme. Toggled from the settings panel (gear icon).
- Checklists: persisted as one JSON blob in `localStorage['orarend-checklists-v1']` (see `loadChecklists`/`saveChecklists` and the `createChecklist`/`addItem`/etc. helpers). This is genuinely private to one browser — no sync across devices, since there's no backend. New checklists get a preset icon per category (`CATS`) and a color cycled from `COLOR_CYCLE` (the same 4 subject accent pairs used elsewhere) — don't add a custom icon/color picker unless asked, that was a deliberate scope decision.
- **Schedule/course data (`EV`/`ONLINE`/`ZOLI_EV`/`CODES`, and every `course_data/<slug>.json`) lives in Supabase's `user_data` table now, RLS-protected — not in static JSON files, and not in `js/script.js`.** `schedule_data/rooms.json` is the one exception, still a live static file (the public university room database, not personal — see below). `js/script.js` declares `EV`/`ONLINE`/`ZOLI_EV`/`CODES`/`ROOMS` as `let` (empty arrays) at the top; `loadScheduleData()` (and `showCourseInfo()` for a single course doc) pull the rest via `Sync.store(key).load()`/`.refresh()` — the same `{load,save,refresh}` contract documented under "Account sync" below, keyed `schedule-ev`/`schedule-zoli`/`schedule-codes`/`schedule-online`/`course-<slug>`. `init()` calls `loadScheduleData()` before the first `rail()`/`renderHead()`/`renderMain()`, same as before. The old `schedule_data/{ev,zoli,codes,online}.json` and `course_data/*.json` files are kept in the repo as reference/backup only (matching how `data/*.xlsx` raw exports are already kept without being served) — excluded from deployment via `.vercelignore`, and **the app no longer reads them at runtime at all.** **At the start of each new semester, update your own data directly in Supabase's Table Editor** (`user_data`, filter by `key`) — or regenerate `supabase/migrate-data.sql` from fresh JSON and re-run it (it's an upsert, safe to re-run) — not by editing the old files, which do nothing now.
- Other people's schedules (e.g. `zoli.json` for a friend's timetable, loaded into `ZOLI_EV`) follow the same `EV` shape (`[dayIndex, start, end, name, room, who, type, pref?]`) and get their own `NAV_LINKS` entry. `zoli.json` is transcribed from that friend's own Neptun export (`data/zoliCourses.xlsx`, same format as `data/myCourses.xlsx`) — prefer re-parsing an updated export over hand-editing individual entries if he changes course, so room/instructor text stays byte-for-byte what Neptun says (a past hand-transcription from a screenshot got both a room name wrong and invented a consultation session that turned out not to exist — the xlsx export is the trustworthy source, a screenshot isn't). `isScheduleView(view)`/`datasetFor(view)` (near the top of the script) are what let `rail()`, `day()`, `week()`/`buildWeekGrid()`, and `renderHead()` work generically across any schedule-shaped view instead of hardcoding `EV` — add a new person by adding their JSON file + a `datasetFor` branch + a nav entry, not by duplicating rendering logic. Room/instructor are optional (`who` may be `""`; the footer template skips the separator when it's empty) since a borrowed schedule often doesn't have that detail. Export (JPG/PDF) always exports your own `EV`, not another dataset — that's deliberate, not an oversight.
- Room search (`ROOMS`, loaded from `schedule_data/rooms.json`, "Teremkereső" nav entry, `renderRoomSearch()`/`renderRoomResults()`): a from-scratch reimplementation of `u-szeged.hu/teremkereso`'s search (room code/name/building lookup), not a live integration with it — that site has no CORS headers and no HTTPS, so it can't be called from a browser at all once this app is hosted, and its data was only reachable by POSTing search terms to its PHP endpoint and scraping the HTML response (no JSON API). **`ROOMS` covers the full university database** (775 rooms, IDs 1–786 with ~11 gaps that are genuinely absent from the source site, not a scraping miss) — scraped once (2026-09) by POSTing a handful of broad substrings (`a`, `e`, `i`, `sz`, plus a targeted `zm` for one building cluster the others missed) to `search.php` and unioning/deduping the parsed HTML results by the site's own stable per-room `id`, rate-limited with pauses between requests since it's a university-managed server. This superseded an earlier, deliberately narrower scope (just the rooms in your own `EV` timetable) once the user decided they'd want lookup coverage for rooms across their whole degree, not just the current semester. To refresh this later (e.g. the university renumbers rooms), re-run the same broad-substring-POST-and-union approach rather than looping over individual IDs — it's a handful of requests instead of hundreds. Because the result set is now large, `renderRoomResults()` shows nothing until you type a query (`"Kezdj el gépelni a kereséshez."`) instead of dumping the whole list, and caps rendered cards at `ROOM_RESULTS_LIMIT` (50) with a "+N more, refine your search" note — both necessary once `ROOMS` stopped being a small, browsable list.
  - Some of `EV`'s room labels don't literally match teremkereső's canonical room name, so matching is done through an optional `aliases` array per room (checked in `matchesRoom()` alongside code/name/dept/address): `IR-213-3`'s canonical name is "Irinyi 213 tanterem" but `EV` calls it "Irinyi 213 PC-terem"; `TIK-002-0` ("TIK Nagyelőadó") is aliased to "TIK Kongresszusi terem" (confirmed with the user — teremkereső has no room literally called that, this was the only large-hall candidate in that building); and `EV`'s "TIK Alagsor I-II. Előadó" is aliased onto *both* `TIK-A01-0` and `TIK-A02-0` since which specific one is used couldn't be determined and the user chose to show both rather than guess. These four are the only entries in `rooms.json` with an `aliases` key — everything else uses teremkereső's name verbatim since there's no `EV`/`ZOLI_EV` label to reconcile it against. If you add a room whose `EV` label doesn't match its teremkereső name verbatim, give it an `aliases` entry rather than editing `name` — `name` should stay what teremkereső actually calls it.
  - **Room cards show a derived location, not always teremkereső's own name.** `parseRoomLocation(r)` splits a room's `code` (e.g. `BO-215-3`) into a building prefix, the room-number part, and a floor — floor comes from the room number's **own leading digit** (0xx=földszint, 1xx=1st floor, 2xx=2nd, ...), a standard Hungarian university convention. It deliberately does **not** use the code's trailing dash-number (`-3` in `BO-215-3`): that's a department/owner id, not a floor — proven by `IR-116-3` (Informatikai Intézet) vs. `IR-116r-0` (Idegennyelvi Kommunikációs Intézet), same room number, different owning dept, different trailing digit. `BUILDING_NAMES` is a **small, deliberately incomplete** map (currently just `IR`→Irinyi, `BO`→Bolyai, `TIK`→TIK) of building-code prefixes we actually know the colloquial name of — the full `rooms.json` spans ~55 prefixes across the whole university (medical campus, arts campus, Hódmezővásárhely, etc.), and inventing names for buildings neither of us has real knowledge of would mean stating facts we can't back up. `renderRoomResults()` only swaps in the derived `"{building}, {roomPart}. terem"` label when the prefix *is* in `BUILDING_NAMES`; otherwise it keeps teremkereső's own `name` and just appends the floor (still derivable, still honest) to the meta line. Don't add a prefix to `BUILDING_NAMES` on a guess — only add one you're actually sure of.
  - The map toggle uses `https://www.google.com/maps?q=<address>&output=embed` (a no-API-key embed URL keyed off the room's address string) instead of the original site's approach (a hardcoded 67-entry address→iframe lookup table in its `get-map.js`) — ours generates the embed from whatever address is in the data, so it isn't limited to a fixed address list.
- Course action sheet: tapping a day-view course card (`.item .card` in `day()`), a desktop week-grid card (`.wcard` in `buildWeekGrid()`), or an online-course chip (`.drchip` in `renderCodepage()`'s `online` branch) opens a bottom sheet (`#courseSheet`/`#sheetScrim`, `openCourseSheet()`/`closeCourseSheet()`) listing things you can do with that course. `openCourseSheet(course)` takes either a scheduled-course object (`{name,s,en,room,who,type}`, from `EV`/`ZOLI_EV`) or an online one (`{name,meta,online:true}`, from `ONLINE`) — the `online` flag is what suppresses the "Terem keresése" button (no fixed room to search for) while keeping "Tantárgy infó". This is meant to grow (more `.sheet-action` rows) as more per-course actions get added — don't build a second, separate popup mechanism for the next one. `.wcard`'s click handler is wired identically to `.item .card`'s — both just call `openCourseSheet()` with the same shape of object — so keep them in sync if the course-card data shape ever changes. Not wired up on the `CODES` page rows (Kötelező tárgyak/Kritérium) either — those already have their own click-to-copy interaction and the same courses are reachable via `EV`/`ONLINE` anyway.
- Desktop week view (`buildWeekGrid()`, ≥1080px): the sidebar's per-day buttons (`#rail .dbtn`) are CSS-hidden at this breakpoint (`display:none`) since all 5 days are already visible in the grid — no JS branch needed, the same `rail()` output just gets hidden. Clicking a column header (`.wh`) instead sets `curDay` and re-renders just the week grid (`week()`), toggling a `.wcol.selected` highlight (gold `--sel` border, independent of and stacking with the existing `.wcol.today` highlight) — a lightweight substitute for a day picker now that there's no separate single-day view to switch to on desktop.
- **The course action sheet is responsive**: it's a mobile bottom sheet (`#courseSheet`) below 1080px (slides up from the bottom, drag-handle bar, rounded top corners only) and becomes a centered desktop dialog at ≥1080px (fixed at `top:50%;left:50%` with a scale+fade entrance instead of a slide, rounded on all corners, a visible `.sheet-close` × button instead of the drag handle) — both variants are the *same* `#courseSheet` element and CSS classes, only repositioned/restyled per breakpoint, not two separate components. `#sheetClose`'s click handler is wired identically to `#sheetScrim`'s (both just call `closeCourseSheet()`) — keep both in sync if the close behavior ever changes. `.sheet-handle` and `.sheet-close` are mutually exclusive via `display:none`/`display:flex` per breakpoint, matching which dismiss affordance makes sense on each (swipe-to-dismiss cue on mobile, explicit × on desktop where there's no swipe gesture). The sheet also has a `.sheet-wide` modifier (toggled by `showCourseInfo()`/`openCourseSheet()`/`closeCourseSheet()`) that widens it for the Tantárgy infó sub-view specifically (600px mobile max-width, 640px desktop dialog width vs. the base 520px) since that view holds denser content than the plain action list — keep the class add/remove in sync in all three functions if the sheet grows more sub-views.
- Tantárgy infó ("Tantárgy infó" sheet action, `COURSE_DOC_ALIASES`, `showCourseInfo()`, `docSection()`): a structured per-course info bank at `course_data/<slug>.json`, built from real course pages saved as PDFs from `unics.szte.hu` (that site needs a login too, so this only works because the user is logged in there themselves and exports the page — same non-scraping constraint as Teremkereső, see above). Each JSON has `name`/`code`/`instructor`/`summary`/`topics[]`/`grading[]`/`rules[]`/`links[]`/`updated` — condensed and reorganized from the source PDF's prose into short bullet points (deliberately *not* a raw text dump, per an explicit user request for "an optimal information bank" rather than "a big chunk of text"), but preserving exact numbers (grading thresholds, deadlines) since those are the parts that actually matter and are easy to get subtly wrong when condensing.
  - **Local JSON reads use `fetchLocal()` (an `XMLHttpRequest` wrapper), never `fetch()`.** `fetch()` unconditionally refuses `file://` URLs in every Chromium engine — confirmed directly (`TypeError: Failed to fetch` / "URL scheme 'file' is not supported"), this is a hard scheme restriction with no settings-based override, not something the Web2APK wrapper's WebView config can fix. Since this app is opened both as a normal page and as `file:///android_asset/index.html` inside that wrapper, any future local-asset read must go through `fetchLocal()`/XHR too, or it'll silently work in a browser and silently fail (empty catch → "nincs feltöltve"-style fallback) in the wrapped app — this exact bug already happened once for `course_data`. XHR to `file://` still depends on the wrapper's `WebSettings.setAllowFileAccessFromFileURLs(true)`/`setAllowUniversalAccessFromFileURLs(true)` (added to `MainActivity.smali` in the external Web2APK project alongside the earlier `INTERNET` permission fix — see History above and DEPLOYMENT.md) — that part could only be reasoned through from documented Android WebView behavior and couldn't be verified locally, since desktop Chromium has no equivalent override and blocks file XHR unconditionally too (confirmed separately) regardless of any setting.
  - The sheet is color-coded per course: `openCourseSheet()` calls `applySheetAccent(course.type)`, which sets `--sheet-bg`/`--sheet-tx`/`--sheet-ac` on `#courseSheet` to that course's existing `--{type}-bg/-tx/-ac` tokens (`type` is `EV`/`ZOLI_EV`'s existing `ea`/`gy`/`pr`/`mt` field; `ONLINE` courses don't have one, so `renderCodepage()` assigns one via `COLOR_CYCLE[i%4]` when building the chip). This is deliberately the *same* four-color system every class card already uses, not a new palette — the info sheet for a course should look like it belongs to that course's card. `GRADE_COLOR_RULES`/`gradeColor()` additionally color-code grading list items by outcome (red→green across elégtelen/elégséges/közepes/jó/jeles) regardless of course accent, since grade-quality color coding is a stronger, more universally legible signal than the subject color for that specific data. Watch for the `\bjó\b` trap if editing these rules: JS's `\w`/`\b` are ASCII-only, so a boundary immediately after an accented vowel like "ó" doesn't match — that's why the "jó" rule uses a lookahead (`(?=\s|\(|$)`) instead of a trailing `\b`.
  - `COURSE_DOC_ALIASES` maps every `EV`/`ONLINE` display-name string to its `course_data` slug, because those names frequently don't match the source page's title verbatim (`EV`'s "Matematika 1. ea." → `matematika-informatikusoknak-1-ea.json`; `ONLINE`'s "MI az egyetemi tanulmányokban" → `mesterseges-intelligencia-az-egyetemi-tanulmanyokban.json`; both `ONLINE` "Webfejlesztés alapjai (ea)" *and* "Webfejlesztés alapjai gy." point at the same `webfejlesztes-alapjai-coursera.json` since Neptun treats the Coursera-based ea/gy as one combined completion). When adding a new course's info, add a `course_data/<slug>.json` file *and* an alias entry for every name string that course appears under — a name that resolves to no alias just shows a friendly "nincs infó" fallback (`showCourseInfo()`'s catch path), it doesn't error.
  - The raw PDF sources live in `course_info_req/` (gitignored — large, and personal-ish exports, not meant for the public repo). The two earlier folders `course_info/`/`course_req/` (plain-text, one file per course, split by info vs. requirements) were an earlier iteration of this same feature and are now unused/gitignored — `course_data/` (structured JSON, info + requirements combined into one file per course) superseded them once the source shifted from hand-typed txt files to real exported PDFs. Don't resurrect the old two-folder txt approach.
- Export (JPG/PDF, in the settings panel) uses `html2canvas` + `jsPDF`, loaded via pinned CDN `<script defer>` tags — the one deliberate exception to "no dependencies" here, since there's no native browser way to rasterize a DOM subtree to an image. `buildWeekGrid()` is reused for both the on-screen desktop week view and the export capture (rendered off-screen via `.export-capture`, which force-overrides the CSS variables to light-mode values and disables the `.wcol` entrance animation, regardless of the active theme). `runExport()`/`exportSchedule()` surface load/render failures as a visible error message (`.export-err`) instead of failing silently — verified working in real browsers; **known not to work in the Web2APK Android wrapper** even with network access fixed, see [DEPLOYMENT.md](docs/DEPLOYMENT.md) — that's a wrapper limitation (no `DownloadListener`), not something to chase in this file.
- **PWA install (`manifest.json`)**: `display: "standalone"` is what makes Android's "Add to Home screen" launch the app in its own chromeless window instead of a bookmarked browser tab with the address bar. Icons are `assets/icon-192.png`/`icon-512.png` (`purpose: "any"`) plus `assets/icon-512-maskable.png` (`purpose: "maskable"`, opaque `--rail` `#20242e` background with the logo inset to a ~70% safe zone so Android's adaptive-icon masking doesn't crop it oddly) — all three generated from `assets/icon.png` (only 100x100 source, so these are upscaled; fine for this flat vector-style mark, but re-generate from a higher-res source if one ever shows up). `<link rel="manifest">` plus the `apple-mobile-web-app-*` meta tags live in `index.html`'s `<head>`; no service worker yet (see ROADMAP.md Phase 1) so it's installable but not offline-capable.
- Font: "Plus Jakarta Sans" via Google Fonts.
- UI language is Hungarian; keep new user-facing strings in Hungarian unless told otherwise.
- **Modules (`modules/<name>/`, `registerModule()`)**: self-contained features (the first is `modules/tanterv-module/`, a curriculum planner) live in their own folder — `css/`, `js/`, any data folder, a `README.md`, optionally `tools/` and a `demo.html` for standalone preview — and are never copied/flattened into the root `css/`/`js/`/`schedule_data/`. A module exposes itself as exactly one global (e.g. `window.Tanterv`), with a `mount(el, opts)`-style API; everything else stays inside an IIFE so it can't collide with `js/script.js`'s own top-level names (`E`, `COLOR_CYCLE`, `CATS`, etc.). All of a module's own CSS must be scoped under one root class (`tanterv.css` uses `.tt`) — never a bare element, `*`, or a class already used site-wide (`.card`, `.crow`, …) — so it can't leak into or be clobbered by `css/style.css`. Like the core, a module's local data reads must go through XHR, never `fetch()` (same `file://`-in-the-Android-wrapper reason as `fetchLocal()`, see History above), and its own script must stay a classic `<script src>`, never `type="module"`.
  - **Wiring a module in is 3 additions to `index.html`, nothing else** — `js/script.js` is never edited per module. A tiny inline bootstrap in `index.html`'s `<head>` (right after the theme-init script, for the same "must run before anything else, zero round-trip" reason) defines `window.MODULES=[]`/`window.registerModule(m)`; this has to live there rather than inside `js/script.js` because a module's own `<script>` tag — and any `registerModule()` call — must run *before* `js/script.js` loads, so its globals (e.g. `Tanterv`) already exist when `js/script.js` builds its nav. Per module: a `<link rel="stylesheet">` for its CSS, its `<script src>`, and a `registerModule({id, label, icon, mount})` call, both placed before `<script src="js/script.js">`. `js/script.js` itself only has three small, permanent, generic hooks that make this work for *any* module without ever naming one: `PAGE_LABELS` and `renderNav()`/`renderNavIcons()` merge `[...NAV_LINKS,...MODULES]` (so a registered module gets a drawer row, a desktop rail icon, and a page title for free), and `renderMain()`'s final `else` branch does `MODULES.find(m=>m.id===view)` and calls its `mount(el)` — the only place the core ever "knows" a module exists, and only by id lookup.
  - Existing built-in pages (schedule, Kurzusok, Teremkereső, checklist) are deliberately **not** retrofitted into this pattern — they stay as they are in `js/script.js`. This is only the extension point for genuinely separate future features, not a mandate to re-architect what already works.

## Security / repo hygiene

- This repo **is public on GitHub** as of 2026-09-09: [github.com/szasz-roland/UniPathway](https://github.com/szasz-roland/UniPathway) (see [DEPLOYMENT.md](docs/DEPLOYMENT.md) for hosting status). Never commit signing keys, `.env` files, API tokens, or a Supabase **service-role** key — see [.gitignore](.gitignore). The Supabase **anon** key in `js/sync.js` is the one deliberate exception: it's designed to be public/client-visible (every Supabase client ships it), and Row Level Security — see `supabase/schema.sql` — is the actual boundary, not secrecy, so it's fine committed in a public repo. Never confuse the two or put a service-role key anywhere client-side.
- The schedule data (professor names, room numbers, course codes) is ordinary public university catalog information, not sensitive — no need to redact it.
- The `android/` build output contains no signing material currently, but double-check before adding gradle/keystore files later.
- Checklist data (shopping items, task names, prices) lives in the visitor's own browser `localStorage`, and — for the one signed-in account, see below — also mirrors to Supabase. It's still real user data, so don't casually wipe/reset the storage key from code.
- `html2canvas`/`jsPDF` are loaded from cdnjs over HTTPS with pinned exact versions (see index.html's `<script>` tags) — if bumping versions, keep them pinned, don't switch to a `@latest`-style URL.
- **Account sync (Supabase, `js/sync.js`, `window.Sync`).** `Sync.store(key)` returns the same `{load, save, refresh}` shape `Tanterv.hybridStore()` already defined (see the module-convention notes above) — any synced feature reuses that one contract. `key` is used as-is for both the localStorage key and the Supabase `user_data.key` column (no prefixing): `orarend-theme`/`orarend-checklists-v1`/`orarend-tanterv-v1` for the per-device-preference data (picks up whatever's already saved there rather than orphaning it), `schedule-ev`/`schedule-zoli`/`schedule-codes`/`schedule-online`/`course-<slug>` for the schedule/course data. Local persistence never depends on being signed in for the *preference* data (theme/checklists/Tanterv) — those work unauthenticated exactly like plain `localStorage`, signed-in-ness only adds the background mirror. The *schedule/course* data is different: with nothing to fall back to locally (see the login gate below), it's genuinely only visible once signed in. There's deliberately no public sign-up UI — one account is created directly in the Supabase dashboard (Authentication → Users); see `supabase/schema.sql`'s header comment for setup, `supabase/migrate-data.sql` for the one-time data bootstrap.
- **The login gate (`#loginScreen` in `index.html`, the `boot()` IIFE at the bottom of `js/script.js`, `Sync.ready` in `js/sync.js`) is what makes the Supabase/RLS protection above actually *real* access control for this app's own data — not just a UI nicety layered on top of a still-public site.** `.shell` starts `hidden`; `boot()` awaits `Sync.ready` (resolves once, definitively, unlike `Sync.onAuthChange`'s immediate-but-possibly-stale first call) and shows exactly one of `#loginScreen` or `.shell` — no flash of the wrong one, no data fetched before the decision is made. A later sign-out reloads the page rather than trying to unwind in-memory state piecemeal. The login screen itself is deliberately unstyled/minimal for now (reuses `.cl-name-input`/`.cl-confirm`, the same classes the settings-panel sign-in form already used) — a real design pass is a separate, later step. This is distinct from, and doesn't depend on, whatever Cloudflare Access ends up doing at the domain level (see the access-control bullet below) — this is RLS enforced by Postgres on the data itself, verified directly (a `curl` against Supabase's REST API with only the anon key, no session, returns nothing for these rows).
- **Domain-level access control (Cloudflare Access) is designed to live entirely outside this repo.** Per the user, it's now been configured — but [DEPLOYMENT.md](docs/DEPLOYMENT.md) may still say otherwise; treat that file, not this bullet's own memory, as the thing to update with the exact current settings, and update [README.md](README.md#deployment--access) together with it. This is a *separate, additional* layer from the login gate/RLS data protection above, not a replacement for it or vice versa — they solve different problems (who can reach the domain at all, vs. whose data a signed-in request can read) and neither depends on the other being in place. Do not add in-app passwords, login forms, or auth middleware **as a substitute for finishing Cloudflare Access specifically** — that reasoning is what the login gate above already had to reckon with directly (a client-side-only gate can't block raw file requests), which is exactly why the data itself moved into RLS-protected Supabase rather than the app just growing a login form that didn't actually protect anything.

## Working style notes

- This is a personal, low-stakes project — prefer small, direct changes over heavy abstraction. It's already split into `index.html`/`css/style.css`/`js/script.js` (the first Phase 1 restructuring step, see ROADMAP.md) — don't re-inline CSS/JS back into `index.html`, and don't split `js/script.js` further into multiple files/modules without a real reason (see the ES-modules note under Code conventions for why not modules specifically).
- **Commit workflow: implement, let the user try it, ask if it's good, then commit.** After finishing a feature/fix, don't commit immediately — wait for the user to confirm it works as expected first, then commit. Exception: pure documentation-only updates (like this file, ROADMAP.md, DEPLOYMENT.md) can be committed right away since there's nothing to "try."
- **Branch workflow: everything happens on its own branch off `main`, never a direct commit to `main`.** Before making *any* change — feature, fix, data edit, or doc update — create a branch (`feature/<short-name>` or `fix/<short-name>`), do the work and commits there, push it, and merge into `main` only once the user has tried it (where there's something to try) and confirmed it's good. `main` is only ever touched by a merge, never a direct commit. This project already has precedent for this (`feature/desktop-centered-layout`, `feature/floating-sidebar` — see `docs/TODO.md`); this rule makes it the default for everything instead of ad hoc/exception-based.
- **Animation and design work goes through `.claude/skills/`.** Before writing any CSS motion or UI polish in this repo, use the relevant skill instead of freehanding it — for this vanilla CSS/JS app that's mainly `find-animation-opportunities` (sweep for what's worth animating and what isn't), `animate` + its `RECIPES.md` (the actual implementation: tool choice, easing tokens `--ease-out`/`--ease-in-out`/`--ease-drawer`, durations), and `animation-vocabulary`/`review-animations` for terminology and self-review. (`animate-expo`, `write-swift`, `pick-ui-library` target other stacks — not relevant here.) This folder is gitignored (third-party skill packages, unclear license) — it's a local tool, not part of the published repo.
